# Design

## Context

첫 change(`add-diary-write`)로 `index.html` + `app.js` 구조가 있다. 현재 `app.js`의 특징:

- 상태는 모듈 변수 `entries` 배열 하나이고, 저장할 때마다 `renderList()`가 목록 전체를 다시 그린다.
- 기록 형식은 `{ id, text, createdAt }`이며 `createdAt`은 로컬 오프셋을 포함한 ISO 문자열이다. `id`는 첫 버전부터 저장되어 있다.
- 날짜 포맷(`formatDate`, `toLocalIsoString`, `displayTime`), IME 조합 처리, 빈 입력 경고 문구(`EMPTY_INPUT_MESSAGE`)가 이미 있다.

동기와 범위는 proposal.md, 동작은 `specs/diary-entries/spec.md`를 따른다.

## Goals / Non-Goals

**Goals:**
- 전체 다시 그리기 방식을 유지하면서 수정 상태를 다룬다.
- 작성 쪽에 이미 있는 포맷·IME·경고 로직을 수정 쪽에서도 그대로 쓴다.

**Non-Goals:**
- 렌더링 방식 변경(가상 DOM, 부분 갱신 등).
- 수정 이력 보관.

## Decisions

### 수정 상태: `editingId` + `editDraft` 두 변수
- 수정 중인 기록의 `id`와 입력칸에 적던 내용을 모듈 변수로 둔다. 수정 입력칸의 `input` 이벤트마다 `editDraft`를 갱신한다.
- `renderList()`는 `editingId`와 같은 항목을 수정 입력칸으로 그리고, 값은 `editDraft`로 채운다. 그래서 수정 중에 위쪽에서 새 기록을 저장해 목록을 다시 그려도 수정 상태와 적던 내용이 남는다(spec "수정 중 새 기록 저장").
- 다른 항목의 [수정]을 누르면 두 변수를 새 항목 값으로 덮어쓴다. 이전 수정은 저장 없이 사라진다.
- 대안: 수정 상태를 DOM에만 두기(그 자리 `<li>`만 바꿔치기) → 변수는 줄지만, 전체 다시 그리기를 할 때마다 수정 상태가 날아간다.

### 이벤트: 목록 요소에 위임
- 항목마다 리스너를 붙이지 않고 `#entry-list` 하나에 `click`, `submit`, `keydown`, `input`을 건다. 버튼은 `data-action`(`edit`·`cancel`)과 `data-id`로 구분한다.
- 수정 줄은 작은 `<form>`으로 감싸 [저장] 클릭과 Enter를 `submit` 하나로 처리한다(작성 폼과 같은 방식).
- 다시 그릴 때마다 요소가 새로 만들어지므로 위임 방식이 리스너 정리를 신경 쓰지 않아도 된다.

### 저장 형식: 선택 필드 `updatedAt`
- 수정하면 `updatedAt`에 `toLocalIsoString(new Date())`를 넣는다. `createdAt`은 건드리지 않는다.
  ```json
  { "id": "...", "text": "책 30쪽 읽음", "createdAt": "2026-11-13T11:30:00+09:00", "updatedAt": "2026-11-13T15:02:10+09:00" }
  ```
- trim한 내용이 기존과 같으면 아무것도 저장하지 않고 수정 상태만 끝낸다(`updatedAt`을 남기지 않음).
- `(수정됨)` 표시는 `updatedAt`이 있는지로 정한다.
- 기존 `loadEntries()`는 바꾸지 않고, 읽어 온 직후 보정 단계를 덧붙여 `updatedAt`이 문자열이 아니면 그 필드만 버린다. 이전 버전 기록은 필드가 없으므로 그대로 "수정 안 됨"으로 읽힌다. 데이터 변환 단계는 없다.
- 혹시 `id`가 없는 기록이 있으면 읽을 때 새 `id`를 붙인다(다음 저장 때 함께 저장됨). 첫 버전은 항상 `id`를 썼으므로 손으로 고친 데이터에 대한 대비다.
- 대안: `edited: true` 불리언 → 단순하지만 언제 고쳤는지 정보가 사라진다. 나중에 수정 시각을 보여줄 수 있도록 시각을 남긴다.

### 공통 로직 재사용
- 빈 입력 경고는 기존 `EMPTY_INPUT_MESSAGE`와 `alert`를 쓰고, 닫힌 뒤 수정 입력칸에 포커스를 준다.
- IME 조합 중 Enter 막기는 작성 입력칸과 같은 조건(`isComposing || keyCode === 229`)을 수정 입력칸용 함수로 새로 만든다. "기존 코드는 두고 기능만 더한다"는 apply 단계의 결정에 따라 작성 쪽 코드는 고치지 않으므로, 같은 조건이 두 곳에 있다.
- 저장 실패(`saveEntries`가 `false`) 시 작성과 같은 실패 알림을 띄우고 수정 상태를 유지한다.

### 포커스
- [수정]을 누르면 수정 입력칸에 포커스를 주고 커서를 끝으로 보낸다.
- 저장·취소 후에는 그 항목의 [수정] 버튼에 포커스를 돌려준다. 키보드로 쓰는 사람이 위치를 잃지 않게 하기 위해서다.
- 수정 중 위쪽에서 새 기록을 저장하면 포커스는 기존대로 위쪽 입력칸에 간다.

### 화면 배치
- 보기 줄: `[날짜 시각 (수정됨)] [내용 ...] [수정]`. [수정]은 오른쪽 끝의 작은 텍스트 버튼.
- 수정 줄: `[날짜 시각] [입력칸 (maxlength=100)] [저장] [취소]`.
- 목록 높이 제한과 스크롤은 그대로 둔다. 수정 줄이 조금 높아질 수 있지만 spec이 "5개 정도"로 정의하므로 수용한다.

## Risks / Trade-offs

- [수정 중 위쪽에서 새 기록을 저장하면 목록을 다시 그려 수정 입력칸의 커서 위치가 사라짐] → 포커스가 위쪽 입력칸으로 가는 상황이라 실사용에서 문제가 되지 않음. 적던 내용은 `editDraft`로 유지된다.
- [수정 중인 항목이 스크롤 밖으로 밀려나 보이지 않을 수 있음(새 기록이 위에 쌓일 때)] → 상태는 유지되므로 스크롤하면 이어서 고칠 수 있다. 자동 스크롤은 하지 않는다.
- [다른 항목의 [수정]을 누르면 적던 수정 내용이 확인 없이 사라짐] → spec에서 정한 동작. 확인 창은 사용 흐름을 끊어 넣지 않는다.
- [같은 기록을 두 탭에서 동시에 고치면 나중에 저장한 탭이 이김] → 한 사람이 쓰는 로컬 다이어리라 수용.
